Dashboard metrics

These are the top-level panels on a cloud load-test dashboard — BlazeMeter, LambdaTest, and the JMeter HTML report all use the same vocabulary.

MetricWhat it capturesSay this in the demo
Regions Geographic locations the virtual users were fired from — US-East, Mumbai, Frankfurt. “We ran from these regions, so this is real-world latency, not localhost.”
Virtual Users Concurrent simulated users active at each moment — the load curve: ramp-up, steady state, ramp-down. “This is the load we applied. Read every other graph against this line.”
Hits Requests sent per second. Throughput as the server experiences it. “How much traffic the server is actually taking, per second.”
Errors Requests that failed — non-2xx responses, timeouts, connection resets — as a count and a percentage. “The number that matters most. Error % rising with user count is the breaking point.”
Response Time Sending the request to receiving the full response. Reported as average, 90/95/99th percentile, and max. “Speed as the user feels it. Quote the 90th percentile — the average hides the slow users.”
Latency Time Sending the request to receiving the first byte back. Time to first byte. “Server thinking time. Response minus latency is roughly the download.”
Bytes Data transferred per second, sent and received. “Bandwidth. A spike here often explains a slow response — heavy or uncompressed payloads.”
Connect Time Establishing the TCP connection plus the TLS handshake. “Network and handshake cost. High here means infra, DNS or SSL — not application code.”
Response Code Distribution of HTTP status codes — 200, 301, 400, 401, 404, 500, 502, 503. “This tells us why: 500 is the app crashing, 503 is the server refusing load, 401 is an expired token in the script.”

The three timings are nested, not separate

A thirty-second demo narrative

  1. Start on Virtual Users — “here is the load ramping from 10 to 100.”
  2. Overlay Response Time — “flat until about 60 users, then it climbs.”
  3. Point at Errors and Response Code — “and that is where the 503s appear. That is our capacity limit.”
  4. Close on Connect Time — “it stayed flat, so the bottleneck is the application, not the network.”

The Aggregate Report table

One row per request. Everything in it is an aggregate over the whole run, so it answers “how did this endpoint behave overall”, not “what happened at minute seven”.

ColumnWhat it means
Element LabelThe sampler name — one row per HTTP call in the plan.
#SamplesHow many times that request executed in total.
Avg. Resp. TimeMean response time across all samples.
Avg. Hits/sThroughput — requests completed per second.
90% line90% of requests finished faster than this.
95% line95% of requests finished faster than this.
99% line99% finished faster than this — only the worst 1% were slower.
Max Resp. TimeThe single slowest request in the run.
Min Resp. TimeThe single fastest request in the run.
Avg. BandwidthKBytes per second transferred for that request.
Error %Share of those samples that failed.
ms / s toggleDisplay unit only. Changes nothing in the data.

Reading the 90 / 95 / 99 lines

Sort every response time in the run from fastest to slowest, then walk up the list. The percentile is simply the value you have reached at that point in the queue.

The average of that run is 1774 ms, which sounds fine. The 99% line says one user in every hundred waited nearly two seconds. That is a real, countable group of unhappy people, and the average never mentions them.

MetricUse it for
90% lineThe typical bad day.
95% lineWhat normally goes into an SLA.
99% lineTail latency — the worst-experience users.
MaxSpotting timeouts and GC pauses. Never a target — one fluke sets it.

Two red flags to call out on screen

  • A row at 100% errors. That request failed every single time. Check its bandwidth — a tiny KB/s figure next to healthy rows means it is returning error bodies, not content. That is a broken or blocked endpoint, not a performance finding.
  • Min 2 ms against an average of 1774 ms. A gap that wide usually means the fast responses are being rejected or served from cache instantly while the real ones crawl.
Order of operations

Fix the errors first. Timing numbers are not trustworthy until error % is close to zero — failures resolve fast and drag every percentile down with them.

VUH — Virtual User Hours

The consumption unit cloud load-testing platforms bill on. It measures how much load you generated and for how long — not how many tests you ran.

VUH = Virtual Users × Duration in hours
Virtual usersDurationCalculationVUH
501 hour50 × 150
10030 min100 × 0.550
50012 min500 × 0.2100
10006 min1000 × 0.1100
1090 min10 × 1.515

The first two rows cost exactly the same. Users and time trade off against each other, so a short enormous test can burn as much quota as a long small one.

The details that actually bite

  • It is peak users, not average. Most platforms bill the maximum concurrency you configured, not the area under your ramp-up curve. Ramp-up time is not free.
  • Duration includes everything — ramp-up, steady state, ramp-down, hold — usually rounded up to the nearest minute.
  • Regions multiply. 100 users from 3 regions is 300 virtual users, so three times the VUH.
  • Aborted tests still consume. Cancel at minute 7 of 20 and you are charged for the 7 minutes that ran; engine spin-up may count too.
  • One virtual user is one JMeter thread. Your Thread Group’s Number of Threads is what drives the bill.

Estimate before you launch

Threads (users) = 200
Ramp-up         = 300 s   // 5 min
Loop / duration = 900 s   // 15 min
Total runtime   = 20 min  = 0.333 h

VUH = 200 × 0.333 ≈ 67 VUH
For a demo

Keep users low and duration short. Twenty users for five minutes costs under 2 VUH and still fills in every percentile and error graph. You do not need heavy load to show the dashboard — you need enough samples for the 90/95/99 lines to mean something.

TermOne line
