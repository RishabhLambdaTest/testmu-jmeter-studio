jmxgen Field Guide

Field guide · authoring JMeter test plans

Everything you need to build a .jmx, two ways

jmxgen turns an OpenAPI spec, a Postman collection, a spreadsheet, a URL list, or a real browser session into a ready-to-run JMeter plan — with dynamic tokens already wired up, and proof it works before you put load on anything. This guide covers both front doors: the desktop app and the Chrome recorder extension.

no Python required macOS · Linux · Windows JMeter 5.6.3 local or HyperExecute

What it actually does

Anything that describes HTTP traffic goes in the left side. A verified JMeter plan comes out the right.

Contracts & collectionsOpenAPI · Postman · cURL · Excel/CSV · a plain URL list
Observed trafficChrome extension · headless recorder · proxy capture · an existing HAR
cleandrop assets, trackers, third parties
→
correlatefind tokens, wire them to ${VAR}
→
verifyvalid XML, JMeter loads it
→
replayrun it once for real
→
runlocally or on HyperExecute

The two highlighted steps are what separate a plan that works from a recording that merely replays.

Correlation is the part people usually do by hand for days. A recorded login sends a CSRF token, a session id, an OAuth code — values that were valid for the ten seconds you recorded and are worthless afterwards. jmxgen finds the value in an earlier response, adds an extractor there, and rewrites every later request to use the variable. Without it, a recorded plan fails on the first replay with stale tokens.

Replay is the second half. Verifying that a file is valid XML and that JMeter can open it proves almost nothing — a plan can pass every static check and still be completely broken, because a JSON path no longer matches or a variable resolves to empty. Replay runs the plan once as a single user against the real target and tells you which request failed and which variable never resolved.

Install

One zip. No Python, no pip, no virtualenv.

first run
$ unzip jmxgen-macos.zip
$ ./jmxgen-macos/jmxgen doctor
   ... first run takes a few seconds while macOS scans the bundle once
       every run after that starts in ~0.2s

If macOS blocks it with “cannot be opened because the developer cannot be verified”, clear the download quarantine flag once:

if macOS blocks the bundle
$ xattr -dr com.apple.quarantine jmxgen-macos
Why a folder, not a single file

A one-file bundle unpacks itself into a brand-new temp directory on every run, and macOS re-scans every extracted file each time — about five seconds per command. The folder is scanned once and then starts instantly. Bundles are per-platform: build on macOS for macOS, Linux for Linux, Windows for the .exe.

If the target machine already has Python 3.8+, there is also a single 144 KB file — dist/jmxgen — that runs anywhere without unzipping anything.

The app

Author a plan in the console

The console is the front door. Everything the CLI can do, it can do — and it shows you what it decided before you commit to it.

  1. Start it

    One command. It opens your browser as soon as the service is actually listening.

    starting the console
    $ ./jmxgen-macos/jmxgen console
jmxgen console  starting on port 8770 ...
jmxgen console  ->  http://localhost:8770
  (ctrl-c to stop)

  2. Pick a source and generate

    Choose what you have — an OpenAPI spec, a Postman collection, a HAR, cURL commands, a spreadsheet, a URL list, or an existing .jmx to import. Upload the file or paste a URL, then press Generate plan.

    The tiles across the top are the summary you should read before anything else: how many requests were kept, how many were dropped, how many dynamic values were correlated, and how big the plan is.

    Every source option, filter and field in that left rail is explained one by one in Every control in the console.

  3. Review what it decided

    This is the step that makes the tool trustworthy rather than magic. The Correlations tab shows every dynamic value it found, which rule fired, how confident it is, and exactly where the value came from and where it is used.

    The Requests tab works the same way: untick a request to drop it from the plan. The Spec tab shows the whole plan as editable YAML, if you would rather work at that level.

  4. Validate — this is the gate

    Press Validate (single user). The plan runs once, for real, against the real target. You get every response code back.

    Don't skip this

    A plan can be perfectly valid XML that JMeter opens without complaint and still be broken — a JSON path that no longer matches, a variable that resolves to empty. Static checks pass; the load test then reports thousands of meaningless failures. Validation is the only step that catches it.

  5. Take the plan

    Download .jmx gives you the file to commit, hand over, or run yourself. Run on HyperExecute creates the project, uploads the plan and its data files, triggers the run, and monitors it.

The app

Every control in the console, and when to touch it

The left rail is four groups: where the traffic comes from, what to keep, how to log in, and how hard to push. You can generate a working plan without opening any of the collapsed sections — they exist for the cases the defaults can't guess.

Source — the dropdown at the top

This is the only choice you must make. It decides what kind of input the console asks you for: some options want a file, some want text pasted in, one takes either.

OptionIt wantsUse it when
OpenAPI / Swagger A file or a URL
.yaml .json		 Your API has a contract. Paste the live spec URL (/v3/api-docs, /swagger.json) and you get a plan with zero recording. Every operation becomes a request; path parameters become ${VARIABLES} rather than being frozen at whatever the example showed.
Postman collection A file
.json, v2.1 export		 QA already built the calls in Postman. Folders become Transaction Controllers, and Postman's own variable chaining (pm.environment.set → {{token}}) survives the conversion into JMeter extractors.
Recording (HAR) A file
.har		 You have a captured session — from the extension, DevTools (Network → Export HAR), Charles, or Fiddler. This is the only source where correlation has something to work with, because it is the only one that contains real responses.
cURL command(s) Pasted text You want two or three specific calls and nothing else. Right-click a request in DevTools → Copy as cURL, paste it in. Multiple commands in one paste become multiple requests, in order. Handles -X, -H, -d, -F and -u.
Excel / CSV sheet A file
.xlsx .csv		 The endpoint list lives in a spreadsheet, or a non-technical colleague owns it. Run jmxgen template to get the sheet with the right columns, hand it over, and feed it back here when it's filled in.
Page URL list (probe) Pasted text
one URL per line		 You have nothing at all — no spec, no recording, no time. It fetches each page, reads the HTML for scripts, stylesheets, images and forms, and builds a realistic page-load plan from what it finds.
Existing .jmx (import) A file
.jmx		 Someone hands you a plan that another tool generated. This turns it back into an editable spec so you can see what is in it, filter it, and re-emit it clean. Pair it with optimize for plans that are bloated or broken.
Which one should I pick?

If your API has a spec, use OpenAPI — it is the fastest path and stays correct as the API changes. If the journey involves logging in through a browser, use the extension and land on Recording (HAR). Everything else is a convenience for input you happen to already have.

Traffic filters — what to keep

These only bite on sources that contain more than you want: a recording, or a probed page. A ten-minute browser session produces hundreds of requests, most of which are fonts, images and analytics beacons that will distort your results and inflate the plan.

Keep: autoThe default, and right most of the time. Keeps pages and service calls, drops static assets and known tracker domains. Use this unless you have a reason not to.
Keep: apiService calls only. Drops every document, image, script and stylesheet — you are left with the XHR/fetch traffic. This is how you turn a browser recording into a pure API load test. On the sample recording below it takes 8 requests down to 1.
Keep: webEverything the browser fetched, assets included. Use this when you are load-testing page delivery — CDN behaviour, cache headers, asset weight — rather than the API behind it.
MethodsBlank keeps every verb. Type POST,PUT to keep only writes — useful for isolating the expensive paths, or for building a test that deliberately hammers mutations.
Include (regex)Keep only URLs matching this. /api/ is the common one. Applied after the Keep setting.
Exclude (regex)Drop URLs matching this, even if they survived everything else. analytics|beacon|hotjar catches trackers that aren't in the built-in list.
Use recorded think timesOff by default, which gives every step a flat 500 ms pause. Turn it on and the plan uses the real gaps between your clicks. Realistic — but if you stopped to read something for two minutes, that pause is now in the plan, so check the numbers afterwards.

Authentication — logging in once, for everyone

Most APIs reject everything without a token. Fill these three fields and the plan gets a login that runs once, before the test starts, with the token shared across every virtual user.

Login requestMethod and path, e.g. POST /oauth/token. Relative to the same host as the rest of the plan.
BodyWhat to send, e.g. {"grant_type":"client_credentials"}. Leave blank for a GET-style login.
Token pathWhere the token is in the response — $.access_token, $.data.jwt, whatever your API returns. Every later request gets Authorization: Bearer ${TOKEN}.
Why this is a separate box and not just another request

It becomes a setUp Thread Group, and the token is published as a JMeter property rather than a variable — because variables are per-thread, so a token extracted by user 1 is invisible to users 2 through 500. Getting this wrong is one of the most common reasons a hand-built plan returns a wall of 401s under load and works perfectly with one user. If you would rather each user logged in separately, leave this section closed and record the login as a normal step instead.

Test data — so 500 users aren't all “bob”

CSV filePath to the data file, e.g. users.csv. It is not uploaded — the plan references it by name, so keep it next to the .jmx when you run. verify warns you if it's missing.
ColumnsHeader names in order, e.g. username,password. Each becomes a variable: ${username}, ${password}. Wire them into the login body or any request.

Without this, every virtual user sends identical credentials and identical payloads — which means your database caches everything and the numbers you get back are fiction.

Load profile — how hard to push

usersConcurrent virtual users (JMeter threads). Leave blank for 1 — correct while you are still building the plan.
ramp sSeconds to reach full load. Ramping matters: 500 users arriving at once measures your connection pool, not your application. A common starting point is roughly one second per user.
dur sHow long to hold that load, in seconds. Anything under a minute mostly measures JIT warm-up rather than steady state.

You can change all three later without regenerating — they are plain fields in the .jmx, and on HyperExecute --concurrency and --duration override them at run time.

The extension

Install the Chrome recorder

Use it when the journey needs your browser — your profile, your SSO, your VPN, your MFA. A headless recorder can't log in as you; this can.

  1. Load it

    Open chrome://extensions, turn on Developer mode (top right), click Load unpacked, and select the jmxgen-recorder/ folder. Then pin it so the toolbar icon is visible.

    Managed Chrome

    Corporate profiles usually block unpacked extensions by policy. Force-install it with the ExtensionSettings policy instead, or publish it to the Chrome Web Store — ./package.sh builds the store zip, and the listing copy and permission justifications are already written.

  2. Leave the console running

    The extension hands its recording straight to the local service, so keep jmxgen console running in a terminal. The popup checks for it and tells you what it found.

    Firefox

    Not supported, and not a matter of effort — Firefox does not implement chrome.debugger, so response bodies cannot be captured at all, and correlation needs them. On Firefox, use jmxgen record or jmxgen capture instead.

The extension

Record a journey

Start from request #1

Type the URL into the popup and press Go. The extension opens the page itself and attaches before the first byte, so the initial document load and every API call the page fires on boot are captured.

This matters more than it sounds. If you open the page first and then press record, everything that happened during page load — the auth handshake, the bootstrap config call, the first token — is already gone. Start recording this tab is there for when you are already deep in a flow and only want the rest of it.

Then just use the site

Log in, click through, submit forms. Popups and OAuth redirects are followed. Redirect chains are kept as separate hops rather than collapsing into the final URL.

The extension

Author steps while you browse

A raw recording captures what happened. It cannot know what you meant. The floating panel is where you say so — without leaving the flow.

ControlWhat it writes into the plan
TransactionEvery request from now on lands in this Transaction Controller — so the report reads Checkout, not twelve anonymous URLs
Assert 200A response assertion on the last request
Assert text…A “body contains …” assertion on the last request
Extract…A JSON extractor on the last response — $.data.token → ${TOKEN}
Pause 2sA Flow Control Action pause after that request
Rename…The sampler label
Skip lastDrops that request from the plan entirely
+ Manual request…A request you type in by hand — never observed, purely authored

Finish

Generate test plan sends the recording to the console and opens it there — you land straight on the review screen from step 3 above, correlations already computed. If the service isn't running, Export HAR instead saves the file and you finish on the CLI:

the fallback path
$ jmxgen from-har jmxgen-session-*.har -o plan.jmx
$ jmxgen replay plan.jmx
How the annotations survive

Every assertion, extractor, pause and transaction name is written into the exported HAR under _jmxgen keys — a custom field the HAR spec explicitly allows. The file stays a completely valid HAR that DevTools and any other tool will still open.

Expect this banner

Chrome shows “jmxgen recorder started debugging this browser” while recording. That is the DevTools protocol attaching — it is the only API that exposes response bodies, and response bodies are what correlation reads. Closing the banner stops the recording.

The two gates, and why there are two

verifyIs this a real JMeter file? Well-formed XML, correct element/hashTree pairing, referenced data files present, no undefined variables. Add --deep and JMeter itself is asked to load it. Fast, no network, safe in CI.
replayDoes it actually work? Runs the plan once as a single user against the real target. Reports every response code, every failed assertion, and every variable that never resolved. This is the one that catches the failures that matter.

Both run automatically in the console. On the CLI, verify runs on the way out of every generating command; replay you invoke deliberately, because it puts one real request on a real system.

You have the .jmx. Now what?

The file landed in your Downloads folder. It is an ordinary JMeter 5.6.3 plan — no runtime, no plugin, no lock-in. Here is the whole path from that file to a report you can show someone.

  1. Put it somewhere sensible, with its data

    If your plan uses a CSV, the plan references it by name — it is not embedded. Keep the two together, and run from that directory:

    the working directory matters
    $ mkdir ~/loadtest && cd ~/loadtest
$ mv ~/Downloads/plan.jmx .
$ cp /wherever/users.csv .          # only if your plan uses test data
$ ls
plan.jmx   users.csv

  2. Sanity-check it before you put load on anything

    One user, one pass, against the real target. Thirty seconds, and it catches the failures that would otherwise show up as ten thousand meaningless errors.

    always do this first
    $ jmxgen replay plan.jmx

== replay plan.jmx ==
  ran 3 sampler(s) as a single user
  PASS - every request succeeded and every variable resolved

    If this fails, fix it now. Nothing downstream is worth doing until it passes.

  3. Run the load test

    This is plain JMeter. -n is non-GUI, -t is the plan, -l is the raw results file, and -e -o generates the HTML report when the run finishes.

    the actual run
    $ jmeter -n -t plan.jmx -l results.jtl -e -o report/

Creating summariser <summary>
Created the tree successfully using plan.jmx
Starting standalone test @ 2026 Aug 27 14:07:02 IST
summary =      5 in 00:00:15 =    0.3/s Avg:   403 Min:     0 Max:  1008 Err:     0 (0.00%)
Tidying up ...
... end of run
    Two rules

    report/ must not already exist and results.jtl must not already exist — JMeter refuses rather than overwriting. Delete them between runs, or use a fresh name each time.

  4. Change the load without touching the file

    The users, ramp and duration you set when authoring become the defaults of JMeter properties. Override any of them on the command line — same plan, different load, nothing edited:

    same file, three different tests
    $ jmeter -n -t plan.jmx -l smoke.jtl   -Jthreads=1  -Jduration=30
$ jmeter -n -t plan.jmx -l load.jtl    -Jthreads=50 -Jramp=60  -Jduration=900
$ jmeter -n -t plan.jmx -l soak.jtl    -Jthreads=20 -Jramp=120 -Jduration=14400

    This is what makes one authored plan usable across a smoke test in CI, a proper load test, and an overnight soak — without three copies of the file drifting apart.

  5. Open the report

    the dashboard
    $ open report/index.html

    JMeter's dashboard gives you response times over time, throughput, error rate, and a percentile table per request. The numbers behind it, from the run above:

    RequestSamplesError %Avg msp95 msThroughput
    listOrders350.03.37.22.56/s
    createOrder330.03.14.92.57/s
    API (transaction)380.058.61007.02.55/s
    Total730.030.68.55.27/s

    Read p95, not the average. The average hides the slow tail that your users actually feel. The transaction row (API) is the whole journey end to end; the rows above it are the individual requests inside it.

  6. Or skip all of that and run it in the cloud

    One command creates the HyperExecute project, uploads the plan and its data files, triggers the run, monitors it, and downloads the artifacts.

    HyperExecute
    $ export LAMBDATEST_USERNAME=...  LAMBDATEST_ACCESS_KEY=...

$ jmxgen ship --jmx plan.jmx --data users.csv \
  --project-name "Orders API" --concurrency 25 --duration 600

    Use this when you need more load than one laptop can generate, load from a specific region, or a run that outlives your terminal. --concurrency and --duration override the authored values the same way -J does locally.

    You can also author and run in a single step, with no intermediate file:

    source → cloud run, one step
    $ jmxgen ship from-openapi api.yaml \
  --author "--auth 'Bearer ${TOKEN}' --include /orders" \
  --project-name "Orders API" --concurrency 10 --regions eastus

    Add --no-run to stop after authoring and verification — the whole first half, as a dry run.

Where the plan runs, and where it doesn't

Nowhere in any of this is jmxgen required at run time. The .jmx opens in the JMeter GUI, runs under jmeter -n, and works in Jenkins, GitHub Actions, Taurus, BlazeMeter, or any other JMeter runner. jmxgen authored it and validated it; after that it is just a JMeter file.

Troubleshooting

First run is slowExpected, once. macOS scans the bundle the first time it executes; every run afterwards starts in about 0.2s.
“Developer cannot be verified”xattr -dr com.apple.quarantine jmxgen-macos — once, after downloading.
Port 8770 already in useThe console names the process holding it and the command to stop it. Or run on another port — jmxgen console --port 8880 — and set the same address in the extension popup under Where jmxgen runs.
The console vanishedIt stops itself after 60 minutes with no requests, so a forgotten window never holds the port. Start it again, or use --idle-timeout 0 to keep it up indefinitely.
Popup says it can't find the serviceThe console isn't running, or it's on another port. Start it, or fix the endpoint under Where jmxgen runs. Export HAR instead works either way.
“Cannot access a chrome:// URL”Chrome forbids extensions from attaching to its own pages. Type your target URL into the popup and press Go instead of recording the current tab.
Recording missed the page loadYou pressed record after opening the page. Use the URL field and Go so the extension attaches before request #1.
replay says a variable didn't resolveAn extractor didn't match. Open the Correlations tab, check what the rule pulled and where from — the response probably changed shape.
Plan targets the wrong domainThe recording was dominated by third-party traffic. Use the traffic filters, or --mode api to keep only service calls.
Recording is huge--mode api drops assets and pages; optimize slims a plan you already have.
