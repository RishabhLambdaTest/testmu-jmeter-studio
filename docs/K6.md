# k6

The same plan, rendered for the other engine.

Everything that makes a plan a plan — correlation, transactions, think times,
which hosts are in and which are out — is decided in the spec, before either
emitter runs. So the `.jmx` and the `.js` are two renderings of one journey. A
difference between them is a bug in one of them, not a matter of opinion.

## Getting one

Generate a plan as usual, then **Download k6 test**. Two files arrive:

| File | What it is |
|---|---|
| `<plan>_load_test.js` | the journey: requests, checks, groups, think times |
| `hyperexecute.yaml` | the job that runs it across machines |

Run it anywhere k6 is installed:

```bash
k6 run plan_load_test.js
```

Nothing else is needed — no Java, no JMeter, no plugins directory. One binary.

## How the plan maps

| In the plan | In the `.jmx` | In the `.js` |
|---|---|---|
| Transaction | `TransactionController` | `group("name", () => {...})` |
| Request | `HTTPSamplerProxy` | `http.request(...)` |
| Assert 200 | `ResponseAssertion` | `check(r, {...})` |
| Extract from JSON | `JSONPostProcessor` | `jsonAt(r, "a.b.0.c")` |
| Extract between two literals | `BoundaryExtractor` | `between(r.body, left, right)` |
| Extract with a regex | `RegexExtractor` | `matched(r.body, /.../, 1)` |
| Extract from a response header | the same, scoped to headers | `matched(headerText(r), ...)` |
| Think time | `ConstantTimer` | `sleep(2.0)` |
| Randomised think time | `UniformRandomTimer` | `sleep(1.0 + Math.random() * 2.0)` |
| Cookies | `CookieManager` | k6's own jar, one per user |
| Follow redirects off | `follow_redirects` | `redirects: 0` |

`${TOKEN}` is JMeter's syntax and JavaScript's alike, so a correlated value
reads the same in both files. A `${...}` the recording happened to contain,
naming no variable of ours, is escaped rather than evaluated — otherwise a page
that printed `${total}` would stop the script from parsing.

## Users, ramp and duration

They are read from the environment, so one file runs at any size:

```bash
k6 run -e VUS=200 -e RAMP=2m -e DURATION=30m plan_load_test.js
```

## Running it from the extension

**Run on HyperExecute…** in the k6 section does the whole thing: creates a
project, uploads the script, and starts the job. No CLI, no repo, no YAML file —
the config travels inside the trigger call.

What happens, in order:

1. A **custom** project is created, named `k6-<plan>` unless you pick an existing
   one. The list shows k6 projects only until you ask for all of them: a load
   test fired into a project holding someone's Selenium suite is a mistake worth
   designing out.
2. The script is uploaded to that project. HyperExecute syncs a project's files
   into the machine's working directory, which is how the script gets there.
3. The job is triggered with the config inline:

```json
{"hyperExecuteConfig": {
   "version": "0.1", "projectID": "…", "runson": "linux", "concurrency": 5,
   "runtime": {"addons": [{"name": "k6", "version": "v0.52.0"}]},
   "matrix": {"shard": ["1","2","3","4","5"]},
   "testSuites": ["k6 run -e VUS=200 -e SHARD=$shard -e SHARDS=5 plan_load_test.js"]},
 "triggerSource": "jmeter-studio"}
```

**Machines come from the matrix, not from the suite list.** Every task receives
the whole `testSuites` list, so five commands would run five k6 invocations on
one machine, one after another. A matrix row becomes its own task on its own
machine, and `$shard` resolves per task. That is why users are divided by
machines here and not in the script.

**No `sourcePayload`.** Left out, the platform defaults to `project`, which is
what pulls the uploaded file in. Setting `projectID` at the top level of the
trigger instead — outside the config — takes a different path that resolves the
project's Git details and fails with `unsupported URL format` for a project that
has none.

**If the machine cannot find the script**, k6 says the file does not exist
rather than anything about a failed sync — the sync logs its errors without
returning them. Check the job's file list before believing the script is wrong.

## The job file, and the trap in it

HyperExecute splits **discovered test cases** across the machines named by
`concurrency`. With one `.js` file and `concurrency: 5`, one machine runs your
test and four sit idle — the job succeeds, and the load is a fifth of what you
asked for.

So discovery emits one line per shard, and every shard runs the same script
with its own slice of the users:

```yaml
autosplit: true
concurrency: 5

testDiscovery:
  type: raw
  mode: dynamic
  command: for s in 1 2 3 4 5; do echo $s; done

testRunnerCommand: k6 run -e VUS=200 -e RAMP=30s -e DURATION=300s -e SHARD=$test -e SHARDS=5 load_test.js
```

**Users in total** and **Machines** on the authoring page write both numbers at
once, so they cannot drift apart. 1000 users over 5 machines is 200 each.

`SHARD` and `SHARDS` are passed to the script so test data can be split per
machine, the way HyperExecute splits a CSV for a JMeter plan.

Run it with the HyperExecute CLI from the folder holding both files:

```bash
./hyperexecute --config hyperexecute.yaml
```

## Why the script has thresholds, name tags and no response bodies

Three things in every generated script that a hand-written one often misses.

**Thresholds, so a failed run fails the job.** k6 documents that *"failed checks
do not cause the test to abort or finish with a failed status"* — only a
threshold changes the exit code. A script with checks alone exits 0 even when
every request failed, and a CI job goes green over a dead server. So every
script carries:

```js
thresholds: {
  checks: ["rate>0.99"],
  http_req_failed: ["rate<0.01"],
},
```

Measured: against a healthy server k6 exits **0**; with the target down it exits
**99**. Loosen or tighten them to taste — they are a floor, not a policy.

**A name tag per request.** k6 aggregates metrics by URL, so
`/api/orders/${ORDER_ID}` would be a different URL every iteration and the
summary would be thousands of one-sample rows. Each request carries
`tags: { name: "GET /api/orders/{order_id}" }` — the shape, not the value, which
is the same name the `.jmx` gives the sampler. The two reports read alike.

**Response bodies are discarded unless something reads them.** `discardResponseBodies: true`
is set for the run, and the requests this plan extracts from or asserts on ask
for theirs back with `responseType: "text"`. A virtual user costs memory for
every body it keeps, and most of them are never looked at.

**The load model is closed**, matching the `.jmx`: `ramping-vus` means a user
starts their next iteration when the last one finishes, exactly as a JMeter
thread does. k6 also offers arrival-rate executors, where load is independent of
how slow the server gets; that is a better model for some tests, and it is a
hand edit away in the options block.

## What k6 cannot do, and how the file says so

A step with no k6 equivalent becomes a comment naming it, and a summary is
written at the top of the file. A test that quietly does less than it says is
worse than one that admits it.

| Left out | Why |
|---|---|
| Browser steps | they ship as the Playwright script instead |
| JSR223 script steps | k6 has no equivalent |
| JDBC steps | k6 needs the `xk6-sql` extension, which is a custom binary |
| A second thread group | k6 runs the first; split them into separate scripts |

k6 is also not a browser: no DOM, no rendering, no front-end JavaScript. It
replays the HTTP calls, which is the load your servers actually feel. Same
limit as JMeter, and the same reason the browser journey ships separately.

## Versions

The job pins the k6 runtime addon HyperExecute documents, `v0.52.0`. The API
this emitter uses — `http`, `check`, `group`, `sleep` — is unchanged in later
versions, and the generated scripts were verified against k6 v2.0.0 locally.
The browser module was renamed between those versions, which is one more reason
these are protocol scripts rather than browser ones.
